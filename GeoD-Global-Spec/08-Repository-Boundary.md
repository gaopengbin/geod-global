# GeoD Global — 独立仓库边界与工程路径

**日期：2026-09-21 · 决策状态：用户已确认 · 实施状态：以第7节实际记录为准。**

## 1. 已确认决定

用户明确询问“是一个新仓库吧，不和现有的国内版混在一起吧？”，在独立目录、独立依赖/配置/构建/发布的说明后回复“可以，开始吧”。据此，GeoD Global 使用独立新仓库，替代初稿中的“同一主干、两套产品壳”建议。

| 对象 | 归属与边界 |
|---|---|
| GeoD Global | `G:\code\geod-global`；独立源码、Git历史、依赖锁文件、配置、测试、构建与发布 |
| 国内版 GeoD | `G:\code\tif-downloader`；维持自己的工作树、依赖、产品入口和发行流程 |
| 当前交互原型 | Global 仓库内的 `prototype/`；用户已认可的界面方向，也是接入真实能力的交互基线 |
| 规格与契约草案 | Global 仓库内的 `GeoD-Global-Spec/`；国内源码链接只作参考证据 |
| 未来共享能力 | 独立版本化包、固定版本的库或可校验产物；各产品自行选择升级时间 |

本轮授权包括本地建仓和隔离工程。远程仓库的实际创建、可见性、推送与发行状态应分别记录；不能因为本地目录已有 `.git` 就声称 GitHub 仓库或安装包已经发布。

## 2. 产品形态保持不变

核心产品是可安装的桌面工作台，目标采用 Tauri 与 Rust 处理本地大文件、任务恢复和成果库。当前浏览器页面是交互原型，后续连接桌面接口；它不证明原生任务、下载或安装包已经完成。

公开网站负责产品介绍、下载、教程与文档。可选 Web 管理台用于经过商业与产品决策的同步、团队协作、远程任务和账单。CLI 与 MCP 是 Global 任务服务的其他入口，使用同一份 Global 契约，不另建一套业务状态。

独立建仓不缩减六大数据域、处理、配方、可靠性、跨平台、推广或商业设计。Cloud/Teams、桌面 Pro 和专业服务的最终组合仍按附件06记录决策。

## 3. 现在落实的隔离要求

| 维度 | 要求 | 验收方法 |
|---|---|---|
| 源码 | 不复制、移动或链接整个国内工作树；Global 的编译输入来自本仓和声明的依赖 | 检查构建配置、导入路径与脚本 |
| 前端依赖 | 本仓声明依赖并提交锁文件；安装到本仓管理的依赖目录 | 使用锁文件安装并构建，不依赖国内 `node_modules` |
| Rust/原生依赖 | 后续加入时在本仓定义 workspace、锁文件与能力打包；不以 `#[path]`、Cargo path跨到国内目录 | 在只含本仓的环境构建对应平台 |
| 开发脚本 | 不自动探测国内 checkout，不设置指向国内的 `NODE_PATH`，不调用国内已装工具作为 fallback | 路径扫描与缺失依赖时的明确失败 |
| 本地状态 | Global 的 app ID、凭据服务名、配置、数据库、缓存和日志空间独立 | 两产品并存时各自写入；显式导入才读取外部文件 |
| 构建与 CI | 每个依赖、工具版本、检查命令由 Global 自己定义 | 干净检出后安装、检查和构建 |
| 发布 | 独立包名、版本、更新通道、签名配置与产物清单 | 不发布到国内更新源；对应平台签名/升级另行验收 |
| 国内工作树 | 保留原有未提交更改、未跟踪文件与任务 | 不执行复制迁移、提交、重置或清理；本轮不宣称修复国内版 |

本轮前端采用根 `package.json` 与根 `package-lock.json` 单一依赖入口；根脚本以 `prototype/` 为 Vite 项目目录。独立依赖不要求启用 npm workspaces，也不保留另一份 `prototype/package.json` 作为重复的安装入口。具体安装与构建结果在第7节记录。

允许文档保留 `G:\code\tif-downloader` 等只读来源链接。禁止的是将这些路径当作构建、测试或运行时依赖；路径检查须区分证据文字与可执行配置，不删掉历史审计来制造“零引用”。

## 4. 未来共享核心的接入规则

共享是可选的技术手段，不是重新合并仓库。需要复用某个下载、格式处理或策略模块时，先明确来源提交、许可证、公开接口、状态归属、异常语义和代表性样例，再形成可版本化交付。

允许的依赖形式：

- 发布的包或 crate，采用明确版本和锁文件。
- 固定不可变提交的库，记录来源与兼容范围。
- 版本化二进制或资源包，记录来源、平台、校验值与许可。

禁止的依赖形式：

- `../tif-downloader/...` 或绝对路径引用国内源码、构建结果、缓存及工具。
- 指向国内目录的 `file:`、`link:`、junction、symlink 或环境变量。
- 借用国内 `node_modules`、临时修改国内依赖，或者缺依赖时自动回退到其他 checkout。
- 未固定版本的远端源码作为可复现构建依据。

Global 桌面、CLI、MCP 可以在 Global 仓库内部共享代码；跨产品库接入不要求两个产品同时升级。共享库发生不兼容变化时，由各产品通过自己的测试和发布门禁后升级。

## 6. 后续工程路径

1. **独立工程基础**：初始化本地 Git，定义忽略规则、项目说明、依赖与锁文件；替换借用国内依赖的启动/构建路径；验证仅靠本仓可安装、构建和预览。
2. **真实检索与预览**：在本仓定义 Item/Provider 类型与错误边界，接入 Earth Search 只读查询；保留样本模式并明确来源，真实结果与 fixture 分开验收。
3. **桌面与任务服务**：建立 Global Tauri/Rust 壳、独立应用存储与最小授权接口；让真实任务状态可持久化，接通下载和取消，再加入恢复、磁盘与完整性检查。
4. **真实成果闭环**：检索 → 预览 → 下载 → 独立验证 → 成果库 → 固定输入配方，产出可打开的真实文件与校验记录。
5. **完整产品扩展**：按既有工作包推进六域、科学处理、时序、CLI/MCP、跨平台与选定商业能力。每次只将确有证据的能力标为完成。

优先完成可见且真实的链路；独立建仓和原型构建是工程基础，不是 GeoD Global 产品交付完成。
