# GeoD Global：开源商业化与官方聚合服务边界

日期：2026-10-09。状态：调研与设计依据；没有启用收费、改变许可证或上线 Pro 服务。当前代码许可依据为 [COMMERCIAL-LICENSING.md](../../COMMERCIAL-LICENSING.md) 和 [GPL-3.0-only](../../LICENSE)。

用户明确的范围：只做二维数据的平台聚合；暂不接商业影像采购、转售、代下单或代收供应商影像费用。未来商业平台连接只面向用户已有的有效授权，并单独核对产品许可与 API 条件。完整方案见 [Free / Pro 与服务点设计](../../GeoD-Global-Spec/16-Free-Pro-and-Usage-Design.md)。

## 1. 开源客户端不能提供不可绕过的本地收费锁

GPL 允许收费分发和商业使用，也允许接收者在遵守许可的前提下修改、复制与再分发。商业用户身份本身不会触发必须向我们付费的要求。本项目的商业许可说明已明确这一点。[GNU GPL](https://www.gnu.org/licenses/gpl.en.html)、[GPL FAQ](https://www.gnu.org/licenses/gpl-faq.en.html)

因此，如果全部能力已经在本地 GPL 代码里实现，用户可以修改会员开关，也可以合规自建或分发版本。代码混淆、离线许可证、签名配置和启动联网检查不能构成可靠的本地收费边界；签名的主要价值是识别官方发行和验证来源。

服务器实际执行的官方服务可以独立要求登录、有效订阅和额度。即使服务端代码以后也公开，自建实例仍不等于拥有我们运营实例上的资源、账户、凭据或配额。收费保护的是运营中的服务访问，不是禁止所有人自行实现相同能力。

不能只把 `isPro` 检查搬到服务器：如果服务器仅返回允许标志、普通 URL 或本地方案签名，实际查询和处理仍全在开源客户端，修改客户端仍可自行完成。新增 Pro 必须有用户愿意购买的真实服务工作。

## 2. 可核对的商业模式

| 产品 | 官方文档说明的模式 | 对 GeoD 的启发 |
|---|---|---|
| Supabase | 可自托管，同时提供官方托管平台；部分托管管理能力不在自托管实例中提供。托管平台采用订阅与用量规则。 | 用户可以自行部署；官方平台卖省去维护、持续运营和资源管理的价值。 |
| GitLab | open-core：同时包含开放源码与 source-available 专有代码；Premium / Ultimate 属于付费档位。自托管实例通过许可证激活付费能力。 | 源码可见不等于全部采用同一种开放源码许可；不能直接类比成给现有 GPL 本地功能加开关。 |
| Red Hat | 订阅包含经过测试和认证的软件、更新、维护与支持。 | 收费可围绕可信维护与支持，而非阻止接收者修改开放源码。 |

## 3. 推荐：开源桌面 + 官方聚合服务 Pro

| 范围 | 推荐包装 | 收费边界 |
|---|---|---|
| 已有公开来源连接、BYOK Agent、本地下载 / 裁剪 / 拼接、文件导出 | Free / 社区版保留 | 已发布 GPL 能力和已有成果不因 Pro 到期受限。 |
| 官方维护的跨平台目录索引、统一在线检索、来源状态检测、去重与一致性维护 | Pro 服务候选 | 官方服务器实际执行服务并验证账号权益；本地直连路线可以并存。 |
| 多地区定时监测、新影像提醒、服务器排程与任务恢复 | Pro 服务候选 | 官方排程和通知资源只接纳有效权益；用户自己运行的本地排程不伪装成不可用。 |
| 托管 Agent、可选云端处理 | 服务点；具体服务可要求 Pro | 服务端调用、受信用量、执行预算和幂等结算；自带模型仍由用户直付模型供应商。 |
| 自建与企业维护支持 | 后续独立服务 | 收取部署、维护和支持费用；不将官方服务访问权默认为任何第三方实例可用。 |

表中的新增服务均为候选，没有被本轮调研变成已实现能力。当前主要是上游直连与本地执行路线，不能仅依据“高级图源列表”就宣布 Pro 已就绪。来源需要注册或申请，也不自动构成我们可收费授予的数据权限。

首个 Pro 服务优先考虑“多地区影像监测”：用户设置多边形、产品、时段与云量条件；官方服务定时查询并维护一致目录、去重和来源状态；发现符合条件的新数据后通知用户，打开完整任务卡预览和确认，再按用户授权下载。该方向与平台聚合一致，有持续工作可计量，也不涉及商业影像采购。上线前需要验证用户需求、真实数据交付、供应商条件与运营成本，不能承诺一定能找到符合条件的完整覆盖。

## 4. 权益需要怎样执行

设计中的官方服务请求应沿以下顺序检查：

1. 服务已上线、输入有效、对应操作满足供应商条件。
2. 验证服务端会话与稳定用户 ID；检查请求资源属于该用户或其获准团队。
3. 读取服务端有效权益，检查额度、并发、速率和用户确认的费用上限。
4. 原子接纳并预占必要额度，由官方执行器实际查询、排程或计算。
5. 保存受信回执、结算已认可用量、释放未使用额度；重试不重复结算。

桌面、网页、CLI 和 MCP 都走同一服务授权规则。修改客户端 `isPro=true`、价格或余额字段不能通过服务端检查。客户端缓存的权益快照仅用于展示，不成为服务端授权依据；不能接受客户端任意自报用量来扣费。

所有支付私钥、托管模型凭据、服务管理员权限和账本写权限留在后端。用户自己的供应商凭据优先留在设备，由用户直连上游；需要官方代访问时才进行明确授权和来源条件核对，不为计费强制上传本地文件。

账户共享通过会话撤销、合理并发、速率与预算控制，不能承诺完全杜绝。其他人可以在许可范围内 fork、自建或自行连接公开来源；我们的优势需要来自维护质量、服务可靠性和使用便利，而非假设源码永远无法被改动。

## 5. 许可路线的选择

当前建议保持 GPL 桌面，不追溯更换已经发布版本的许可，不减少既有本地权利。未来如果选择独立专有组件、open-core 或双重许可，需先核对代码权属、贡献者授权、第三方依赖与组合分发边界；把代码放进另一目录不自动解决 GPL 义务。

“公开仓库”“源码可见”“开放源码许可”“官方服务免费”是不同概念。未来是否公开服务器实现是单独的产品决定；无论是否公开，官方实例的访问控制和真实服务价值都必须存在。

## 6. 本轮落点

- 在收费设计中撤掉商业影像采购、代购报价、影像采购 SKU 和代收供应商费用。
- 85 项目录中的商业平台项改为“自带授权的平台聚合候选”，原接入状态保持不变。
- 目录中该候选的中英文说明移除订单描述；没有实现供应商连接或在线收费。
- 配置草案标记本地 GPL 收费锁无保证、客户端 Pro 标志不受信、官方后端必须实际执行服务。
- 价格和点数继续保留为未上架草案；当前没有支付上线、商户申请、许可证变更或对本地用户收费。
