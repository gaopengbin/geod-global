# 主要流程失败诊断补齐与验收

核验日期：2026-10-22。延续之前 COG 预览修复，补齐主要流程的安全诊断字段；不新增管理界面。

## 统一记录

失败事件新增：阶段 `stage`、固定原因码 `reason`、可获取的 `httpStatus`、可获取的 `retries`、阶段依据 `diagnosticOrigin`。关联既有 `operationId`、产品版本、来源、入口、结果状态和耗时桶。禁止任意文本字段与原始错误、网址、文件路径、区域、模型对话或凭据。

`explicit` 表示失败边界直接捕获；`classified` 表示根据所属操作/有限错误模式分类；缺信息如实 `unavailable` 或 `unknown`。这不是将所有失败自动认定为已找到底层根因。历史19次事件不具备新字段，不能追溯补造。

| 主要流程 | 此次补齐 |
| --- | --- |
| 检索/翻页 | 请求、JSON解码、目录校验；HTTP错误保留状态，翻页操作仍由原操作上下文区分 |
| 授权 | 公共临时签名请求保留授权阶段、HTTP状态及重试次数，不保存签名本身 |
| COG与产品预览 | 元数据、切片与解码失败的上下文；HTTP状态和重试数不再被安全显示消息抹掉 |
| 下载 | 提交队列失败与后台任务失败分开；后台 SHA-256 mismatch 分类到成果校验 |
| 成果/处理 | 保存项目、检查/打开成果、处理配方、导入导出等操作记录安全分类；公共地图/矢量客户端保留可获取的HTTP状态 |
| Agent/模型 | 派发、确认、模型测试及终态分开；异步回合失败使用可获取的 session.error 进行固定分类 |

部分原生后台或模型提供方只有字符串错误而无结构化内部阶段；只能报告操作边界和分类原因，内部子阶段、重试次数继续标为未知。没有通过改变用户数据采集范围来假装补齐底层根因。

## 验证证据

所有文件在 `.verification/usage-diagnostics-20261022/`：

- `roundtrip.json`：实际客户端统计器通过正式HTTPS上传，接收端200且精确确认事件ID。
- `readback.json`：独立固定主机密钥SSH，SQLite `mode=ro` 回读本批15条事件，7条失败均有全部诊断字段，全部为 development，不并入正式用户统计。
- 真请求：本仓库原生服务的不存在成果检查返回400/not_found；无效下载提交返回422；Earth Search实际拒绝负数 limit 返回400。测试没有创建下载任务。
- 可控故障：真实本地HTTP端点持续503验证预览三次尝试/两次重试；损坏JSON验证 catalog_decode；受控原生模型调用执行HTTP请求后返回503，验证 model_test；后台校验失败使用受控任务状态验证关联。受控模型场景不等于调用了真实外部模型。
- `deployment.json`：接收端 release `20261022T021912Z`，SHA-256 `26076ab5577a2322703c03321342226d69e064d26efea7919d89f649971d4022`。服务健康，保留旧release与SQLite备份；没有修改Nginx、公开报告权限或数据库表结构。
- 586项Node单元测试、22项相关OpenLayers/React集成测试、7项Python接收端测试通过；生产构建通过。
- 接收端测试逐一验证新字段内放入私有URL会被400拒绝；客户端验证原始敏感测试文本未进入上传事件。

## 交付状态与使用

线上接收端现已兼容新旧字段，报告增加 `diagnostics` 聚合。客户端源码和本地运行版已接入；此前发布的冻结桌面安装包尚未更新，安装旧包的用户不会自动得到新诊断字段。正式发布新版客户端后，才能用新字段持续观察外部用户失败。

继续通过 `docs/usage-analytics.md` 中的独立接收端查询，不去CDN控制台查客户端失败，也不把开发故障测试算作用户失败。
